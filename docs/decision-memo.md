# Design Defense Memo

**To:** the Week 8 design reviewer
**From:** Dranzer Rogue
**Date:** 2026-10-04
**Re:** `docs/architecture.md` v0.1, in defense before you attack it

This memo does four things the technical specification itself can't do: argue against my own weakest decision, name what I'd most regret, state what gets cut if I lose real time, and give an honest accounting of where an assistant did and didn't do the thinking. None of it is polished. It's supposed to be true instead.

## 1. The decision I'm least sure about: one node per role-type, not one per unit

`docs/architecture.md` §6 settles agent-node granularity at one process per role-type — Medical, Fire, Shelter, Security, plus Incident-Command. Five processes per run, not the 25-40 a literal reading of `docs/requirements.md`'s own definition of "Node" ("a software process running one agent instance") would suggest.

Here's the strongest case against that, and I mean it: the entire pitch of this project, going back to `PROJECT.md`'s Architecture section, is that no single role has full authority and there's no single point of failure. Five processes doesn't really deliver that. If the Medical node goes down, every Medical unit goes dark at once — the blast radius of one failure is now a whole category of responders, not one ambulance. That's a worse failure mode than the one-node-per-unit design would have had, and it's exactly the kind of thing FR-DEGRADE-01's heartbeat detection exists to catch, which means I built real machinery to detect a failure mode I made structurally worse. A reviewer who read the architecture closely before reading this memo would be right to ask why "decentralized" gets diluted the moment it costs real build hours.

I'm proceeding anyway for one reason, and it's not that the tradeoff disappears — it's that the thing being decentralized isn't what I first implied. This system is a demonstration machine, not a real-time scenario tracker. Nobody's life is actually riding on a Medical node staying up during a batch competition run or the capstone defense demo; what's riding on it is how convincing the demo looks and how clean the comparison between team sizes comes out. If this were a real operational tool, I don't think one-node-per-role-type would be defensible, and I'm saying that directly rather than arguing myself out of the problem. At demonstration scale, the cost of a role going dark is a bad run that gets logged and retried, not a missed emergency. That's a real distinction, but it's also a decision I'm making about what this project actually is, not a technical finding that makes the concern go away.

## 2. The decision I'd most regret: the confidence-60 stand-in threshold

ADR 0006 sets the batch-mode stand-in policy — the thing that lets unattended scoring runs proceed without a real human sitting through every escalation — to approve automatically at confidence ≥ 60. That number is a guess. I'm standing by it, but only until it's actually tested, and I want to be honest that "standing by it" right now means "haven't been shown it's wrong yet," not "have evidence it's right."

The earliest signal that would tell me it's wrong is already written into ADR 0006's own revisit trigger, and I'm naming it here on purpose instead of letting it sit quietly in an ADR nobody re-reads: once Milestone 5's Spike SP-03 actually runs `llama3.2:3b`'s real confidence scores against a labeled test batch, if the 60 threshold approves fewer than 50% or more than 95% of the escalated cases, it isn't doing real separating work and every batch score built on it so far is suspect.

What keeps this from being my top regret instead of my second one is that it's cheap to fix. It's one number in one policy, not a structural commitment like the node-granularity call — if SP-03 comes back ugly, I recalibrate the threshold and re-run the affected batch competitions. That's a real mitigation, not a hope.

## 3. My cut line: what goes first if I lose three weeks

If illness, a failed integration, or anything else ate three weeks, the first things out are the zone-boundary display (FR-MAP-01), unit position tracking (FR-MAP-02, already Could-priority and already out of scope in the current design), and network-partition recovery (FR-DEGRADE-03/04 — my own Week 4 rationale already called this a likely stretch goal before I ever got here). None of the three touch the actual reasoning pipeline; they're display and resilience layers on top of a system that still runs and still produces a defensible result without them.

What survives is the part the capstone is actually about: incident intake, classification, the contract-net negotiation and tiebreak logic, the audit trail, and the written report. A dispatcher demo without a zone map on screen is a worse demo. A dispatcher demo without the negotiation actually happening is not this project.

## 4. The AI honesty call

This is the part I don't get to soften. Across this project, the assistant drafted nearly everything that ended up in `docs/tech-evaluation.md`, the ADRs, `docs/architecture.md`'s interfaces and data model, and this week's spike. I made a specific, countable set of calls myself: the model (`llama3.2:3b`), the novelty-load demotion in Milestone 5, and in Milestone 6 the node granularity, the primary-key style, the migration approach, the password hashing, and the batch-vs-interactive split this memo's §1 and §2 are about. Everything past those calls is reasoning I accepted, not reasoning I generated.

The one thing I'm certain the assistant could not have made for me is the actual transition call — fully committing to the pivot `PROJECT.md` describes, away from a live real-time incident tracker and toward a scripted, after-the-fact demonstration tool. That pivot happened on 2026-09-04, on paper. It did not fully happen in practice. When the assistant helped me write the non-functional requirements the following week (2026-09-20, logged in `docs/ai-usage.md`), the result still reads like a real-time operational tool — a 45-second dispatcher decision window, a web UI whose controls have to stay keyboard-reachable mid-incident, language that assumes someone is sitting at a screen reacting to something actually happening. Those aren't neutral details; they're the fingerprints of the live-event-handler framing I'd already told it to move past. The assistant kept reusing patterns from before the pivot because I'd set those patterns myself early on, and without me actively catching and overriding it, it defaulted to continuing them rather than questioning whether they still fit.

I know this isn't hypothetical, because it happened again this week, in front of me. Building this milestone's architecture, the assistant had to stop and flag a direct contradiction between `PROJECT.md`'s unattended batch competition (nobody watching 45-250 runs) and `docs/requirements.md`'s FR-AGENT-03 (a human must approve every low-confidence or high-severity proposal) — the same live-tool residue, still unresolved three milestones later, now forcing an actual architectural decision (ADR 0006) instead of just a sentence that didn't quite fit. That the assistant caught it and asked me, rather than silently picking one reading and building past it, is the correct behavior. That the contradiction existed at all, three milestones into a project I'd already pivoted, is the part that's on me and on how I was directing it — not a reasoning failure of the model, a failure of me not fully re-deriving the downstream documents after I changed the premise upstream. An assistant can draft around a stated decision. It can't notice that I never finished making it everywhere the decision actually touches. That part has to be me, checking my own older work against my own newer decisions, every time I change my mind about what this project is.
